## Conclusion

**Class: planning. Confidence 0.95.**

- **Root cause.** D0021 (items 2, 5 and 7) and task T0339 give the O003 successor experiment the id `E009`.
  D0014 had already given that id to O007's experiment, the scikit-fem thermal reference. That experiment was
  registered and run to completion on 2026-11-07, and claim C004 rests on it. O003 also depends on it

  `experiments/runners/e009_run.py` is replaced. Registering the draft would then overwrite O007's registered spec.
  Both T0339 attempts correctly stopped, wrote nothing, and so failed every file-dependent DoD command.
- **Why the label said "implementation".** That label came from an mfos routing defect, not from the work:
  - the scientist report schema has no `status` field, so the orchestrator cannot see a scientist's "blocked";
  - so it ran the DoD, recorded `dod_failed`, which mfos maps to `implementation`;
  - it then retried the same packet automatically, and the second attempt blocked for the same reason;
  - this diagnosis was spawned only when the attempts ran out.

## 4. Contributing tooling defects (FACT unless marked)

These did not cause the planning error, but they turned a blocked task into a mislabelled, repeated one.

**D1: a scientist cannot report "blocked" in a form the orchestrator sees.**
- What happens:
  - `loop._verify` treats a run as blocked only if `out.get("status") == "blocked"` (loop.py:433).
  - `ScienceReport` has no `status` field and `extra="forbid"`: `ScienceReport.model_validate({"summary": "x",
    "status": "blocked"})` raises ValidationError (my test, exit 0).
  - Only `BuildReport` has `status`.
- Yet the packet ("stop and report `blocked`") and the scientist prompt both tell scientists to report blocked.
- Result:
  - the block went through `gates.run_dod` and became `dod_failed`, which `SIGNAL_CLASS` maps to `implementation`;
  - `diagnose.respond` then returned `repair`, so the identical packet ran again ($0.86);
  - after that it returned `diagnose`, which spawned this task.
- Had the block been visible, it would have been routed as `attempts_exhausted`, which maps to `planning`, and would
  have gone to the founder.
- The agent's own `failure_class: planning` is ignored for design tasks.
- No open inbox item tells the founder about the collision (FACT: `grep T0339` over the main checkout's
  `project/inbox`: only I0196, answered, and I0198, approved).

**D2: no pre-merge check would have caught a compliant overwrite.**
- The DoD's final `git diff --quiet` guard protects `experiments/runners/e008_run.py` but not `e009_run.py`.
- The fast gate (ruff and unit tests) does not run `mfos doctor`.
- The full gate, which includes `doctor --ci`, runs before merge only for high- or critical-risk tasks
  (`loop._full_gate_ok`), and T0339 is medium risk.
- INFERENCE: if an agent had followed the packet literally, the only pre-merge safeguard would have been the critic
  review. CI's doctor would have flagged the damage only after the merge.

**D3: `register()` and `validate_draft()` do not refuse an id whose `specs/<id>.yaml` is already registered** (T4).
