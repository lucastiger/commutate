  other agents loaded the Mac at that moment.

## E1 against E4: partly separated by tests 1 and 5
- **Fact:** the same tests on the same commit took 984 s in test 1 and about 740 s in test 5, at similar load averages
  (about 5 to 6). The user CPU time itself fell from 964 s to 740 s. So the same work cost 30 % more CPU time in one run
  than in the other.
- **Inference:** under a load near the core count, the process is sometimes placed on efficiency cores, or is slowed by
  heat or shared-cache contention. That slows it without lowering its 99 % CPU share. This matches the ±25 %
  load-dependence recorded for l2_layout timings in `src/moduleforge/solvers/l2_layout.py`.
- **So the truth lies between E1 and E4.** The fast suite's runtime under normal multi-agent load straddles the
  900 s limit, at about 740-980 s. Whether the gate passes is a matter of timing luck, not of the branch. That is a
  flaky gate.
- An idle-machine baseline is still unmeasured. `ps` and `sysctl` are denied in the sandbox, and two other agents
  share the Mac. The 2026-10-31 policy note records the whole suite at 411 s "alone". The suite has grown since then.

## Conclusion
- **Class: infrastructure.** The fast-gate budget (900 s per command) sits inside the spread of the fast unit suite's
  runtime on this Mac under multi-agent load: 740 s in one run and 984 s in the other, on the same commit. Confidence
  0.85.
- **Not this branch.** E2 and E3 are refuted by tests 1 to 3. On this HEAD the gate both failed (by the orchestrator,
  and by the pytest step's 984 s in test 1) and passed (test 5).
- **Every branch is affected.** Each branch merged with current main inherits the risk, as T0396 shows. Main's next
  merge (T0385 adds `tests/unit/test_fasthenry_run.py`) can only add time. No change in this task's write scope
  (`research/**`, `experiments/drafts|runners/**`, `tests/acceptance_drafts/**`, `project/memory/**`) can shorten
  `tests/unit`.
